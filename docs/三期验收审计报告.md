## 5. 差距报告

### G-1 调度/运行时/资源操作未接入统一审计（**高**）

`scheduler.py`、`executor.py`、`runtime.py`、`resources.py` 中对 `audit` 的引用数均为 **0**。
平台最有权限的四类操作（起进程、跑运行时命令、占资源、批准计划）都不写 `audit_logs`。

它们各自有专用表（`dispatch_events` / `runtime_action_runs`），但：
- 审计查询接口 `/api/audit-logs` 看不到它们
- 无法按「谁在什么时候做了什么」统一回溯

### G-2 自主调度从未完成一次真实执行（**高**）

- `dispatch_plans`：1 行
- `dispatch_items`：**0 行**（计划里没有任何调度项）
- `runtime_action_runs`：1 行，且是只读的 `docker ps`

原因：全局开关 `AGWS_PLATFORM_EXECUTOR` 默认 off，两个项目也都没开 `execution_enabled`。
**这是刻意设计**，但意味着「全自动执行」这条价值主张目前没有任何生产证据。

### G-3 跨项目协作能力零使用（**中**）

`task_dependencies` 0 行、`shared_resources` 0 行、`resource_claims` 0 行。
代码与测试都在，但没有任何真实跨项目协作发生。

### G-4 三期未合并到 main（**高**）

8 个提交全部停留在 `feat/phase3-m3-0-foundation`。`main` 仍是三期前状态。
接手者若从 `main` 拉代码，看不到任何三期能力。

### G-5 无正式验收报告（**高**）

`docs/` 下只有 `handoff-2026-11-04.md`、`三期建设方案.md`、`项目纳管约定.md`。
没有验收结论、风险清单、签字项。按一期二期的惯例，验收应产出
`ai-team/reports/*-acceptance.md` 形式的文档（PASS / PASS WITH RISKS / FAIL）。

### G-6 文档状态自相矛盾（**低**）

`docs/三期建设方案.md:17` 仍写「M3-0 进行中」，但同文件完成清单 4 项全部打勾。

### G-7 权限模型只有二值（**中**）

没有角色、没有项目级授权。持令牌的远端可操作全部项目，包括运行时动作与调度执行。

### G-8 移动端链路未实测（**中**）

Tailscale 客户端处于 stopped，手机访问 8099 的实际链路从未验证。
代码层（鉴权 + 响应式）已就绪。

### G-9 环境类未解决项（非代码）

- 历史项目管理平台 8080 从本机不可达
- Tailscale 停止

## 6. 对「进入 P4-M0」的判定

用户设定的闸门是：**第三期验收完整，才进入 P4-M0**。

按现有证据：

| 闸门条件 | 状态 |
|---|---|
| 存在 P3-M8 且已验收 | ❌ P3-M8 不存在 |
| 三期有正式验收结论 | ❌ 无验收报告 |
| 三期成果在主干可用 | ❌ 未合并 |
| 核心能力有真实运行证据 | ❌ 自主调度 0 次执行 |

**结论：闸门不成立，不应进入 P4-M0。**

同时，`P4-M0` 在本机任何位置都没有定义，无法确定其范围与验收标准。

## 7. 建议的补齐顺序

若要达成「三期验收完整」，按依赖排序：

1. **合并到 main**（G-4）——先让成果成为主干事实
2. **补审计接入**（G-1）——调度/执行/运行时/资源写 `audit_logs`
3. **跑一次端到端真实执行**（G-2）——material 项目开 `execution_enabled`，跑一个低风险任务，留存证据
4. **产出验收报告**（G-5）——结论 + 风险 + 证据链接
5. 修文档状态（G-6）
6. 视需要补权限模型（G-7）与移动端实测（G-8）

其中 1–4 是「验收完整」的必要条件，5–6 可作为遗留风险披露。
