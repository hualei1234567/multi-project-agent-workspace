## 关键设计决策

### D1 · 五层实体分离

`project_agents` 是**实例**（某项目某角色某 worktree），Registry 是**定义**。
一个定义可实例化到多个项目。混为一谈会让「这个角色有哪些能力」变成
「这条实例现在是什么状态」，语义完全不同。

### D2 · Registry ≠ capability_listings

- Registry：「系统里**存在**什么」
- `capability_listings`：「某项目**被授权用**什么」

强行合表会重蹈 R5「多来源数据混在一张表」的覆辙。

### D3 · 心跳超时在读取时计算

如果靠采集线程改 `status`，线程一旦挂掉，status 会永远停在 `healthy`——骗人。
读取时用 `heartbeat_at + ttl < now` 计算，永远不会骗人。

### D4 · 兼容矩阵默认宽松

全矩阵记录不现实（角色×技能×模型×运行时组合爆炸），默认拒绝会让新资源
无法使用。所以：**没有记录 = 兼容**，只有显式 `compatible=0` 才拦截。
这是显式决策，写在契约里，不是疏忽。

### D5 · 能力必须带 evidence

V4.0 要求能力声明有依据。空 evidence 不禁止登记，但评分 ×0.5——
诚实优于完美。

## 与调度器接线（关键）

Registry 最大的风险是「建了不用」。所以在 `scheduler._skip_reason` 里加硬过滤：

```python
if registry_blocked and agent["role_key"] in registry_blocked:
    return registry_blocked[agent["role_key"]]
```

**实测验证**：
```
active 时:   ['reg-verify-1']  ← 可调度
revoked 后:  []                ← 剔除
原因:        ['角色在 Registry 中已撤销']
```

测试 `test_revoked_role_excluded_from_scheduling` 锁定该行为。

**降级保护**：表不存在时（老库未迁移）返回空 dict，不能因为 Registry
没建就把整个调度打死。
