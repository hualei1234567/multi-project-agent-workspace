### 验收脚本抓到的真实问题

这是「不能只管开发」的直接体现——脚本建立后立刻抓出三个问题：

   `capability_listings.source_project_id`、`knowledge_grants.source/target_project_id`。
   一条 parse error 让整个清理 SQL 回滚。

三个都已修复：
- 清理改为**按 schema 动态生成**，自动覆盖新增表
- 按 `pragma_table_info` 取真实列名
- 清理时 `PRAGMA foreign_keys=OFF`（37 张表互相引用，手工排序不可靠）
- 清理后自检项目是否真的没了

## 三、GitHub Actions CI

### 3.1 结构

```
ci.yml
├── python           pytest + ruff + py_compile（与 test.sh 等价）
├── route-contract   独立 job：契约漂移单独可见
├── ui-smoke         隔离实例 + 浏览器冒烟（needs: python）
└── ci-gate          聚合，给 Branch Protection 一个稳定 Required Check
```

### 3.2 关键设计决策

| 决策 | 理由 |
|---|---|
| 只装 pytest + ruff，锁定版本 | 平台运行时纯 stdlib，零第三方依赖 |
| UI 冒烟用**同一个** `scripts/ci-smoke.sh` | 本地与 CI 条件不一致是「本机绿 CI 红」的根源 |
| 隔离实例（临时库 + 临时配置） | 绝不碰仓库里的 `data/platform.db` |
| npm ci 失败回退官方 registry | lock 文件的 resolved 指向作者本机镜像 |
| `permissions: contents: read` | 最小权限 |
| 不做部署、不自动合并 | 修复包 §6 明确禁止 |
| `concurrency` 取消旧运行 | 避免排队浪费 |

### 3.3 本地完整模拟验证

CI 不能只提交就完事。本地用同样的命令跑通：

```
[1/4] 浏览器 ✅     [2/4] sqlite3 ✅
[3/4] 实例 ✅       [4/4] UI 冒烟 157/157 ✅
```

### 3.4 GitHub 安全要求核对

| 要求 | 落实 |
|---|---|
| Secret 受控，不打印 | CI 不使用任何 Secret |
| PR 来自 fork 限制权限 | 默认 `contents: read` |
| 不自动绕过 Branch Protection | 未配置任何绕过 |
| 不执行未审查的外部脚本 | 只跑仓库内脚本 |
| 不自动部署生产 | 无 deploy job |

## 十、CI 首次运行的实战发现（2026-11-15）

> 这一节记录的是「只写不验」会漏掉的东西。

### 10.1 第一次运行：失败

`Python · pytest` 失败，`tests/test_openapi.py::test_served_over_http`
报 `HTTP Error 503: Service Unavailable`。

### 10.2 第二层原因：测试请求被送去代理

GitHub runner 配了 `http_proxy` 环境变量，`urllib.request.urlopen` 默认读它，
于是对 `127.0.0.1:<随机端口>` 的请求也被送去代理。
**本地开发机没有代理变量，这个问题本地永远不会出现。**

修复：`app/tests/conftest.py` 新增 `local_urlopen`（`ProxyHandler({})` 的 opener），
6 个测试文件全部改用。

### 10.3 第三层原因：测试没搭好自己的环境（真正根因）

改完代理仍失败。深入排查发现 503 不是代理返回的，是**服务端自己返回的**：

- 测试直接构造 `Handler` 起服务，不走 `main()` 的 `bootstrap()`
- 空库上 `resolve_principal()` 查 `principals` 表报 `no such table`
- R1 的 S-5 fail-closed 治理闸门正确返回 503

**这不是产品缺陷**——fail-closed 正是 R1 要的行为。
真正的缺陷是测试依赖本地已存在的 `data/platform.db`，
而 CI 的干净 clone 里 `data/` 被 gitignore 掉了。

修复：测试自己建临时库并 `init_db`。

### 10.4 验证方式（与 CI 条件完全一致）

```bash
git archive HEAD | tar -x -C /tmp/cicheck2      # 干净树，无 data/
cd /tmp/cicheck2/app
http_proxy=http://127.0.0.1:9999 HTTP_PROXY=http://127.0.0.1:9999 \
  python -m pytest tests -q
# → 403 passed
```

代理变量指向无效端口，任何真实外发请求都会失败；
本地实例请求用 `local_urlopen` 绕过。

### 10.5 教训

| 问题 | 本地能否发现 |
|---|---|
| 环境代理污染本地请求 | ✗ 本地无代理变量 |
| 测试依赖本地已存在的数据库 | ✗ 本地有 `data/platform.db` |
| CI YAML 语法 | ✗ 需真实解析器 |

三条都只有**真正跑一次 CI** 才能暴露。
这正是 R4 把「push 后观察结果」列为必要步骤的原因。

### 10.6 第四层原因：仓库里提交了本机专属配置

第三次运行后 Python 与 Route Contract 都通过，UI Smoke 失败：

```
npm error ECONNREFUSED 127.0.0.1:17890
npm error request to https://registry.npmmirror.com/playwright-core/... failed
```

根因：仓库**提交了 `.npmrc`**，内容是作者本机配置：

```
registry=https://registry.npmmirror.com
proxy=http://127.0.0.1:17890
https-proxy=http://127.0.0.1:17890
```

CI 上没有这个代理，npm 直接连本地端口 → 拒绝。

修复：
1. `.npmrc` 从索引移除（磁盘文件保留，本机 npm 不受影响），
   加 `.gitignore` + `.npmrc.example` 说明哪些内容是本机专属
2. `package-lock.json` 的两处 `resolved` 由 `registry.npmmirror.com`
   改为 `registry.npmjs.org`（**只换下载源，integrity 与版本完全不变**）

### 10.7 CI 排查路径汇总（四层，逐层剥开）

| # | 现象 | 真因 | 本地可复现 |
|---|---|---|---|
| 1 | pytest 失败 503 | 测试请求被 `http_proxy` 送去代理 | ✗ |
| 2 | 仍 503 | 测试没建库，fail-closed 治理闸门返回 503 | ✗（本地有库） |
| 3 | UI Smoke 失败 | 仓库 `.npmrc` 写死本机代理 | ✗ |
| 4 | — | lock 的 resolved 指向镜像 | ✗ |

**四层全部只有真正跑 CI 才暴露。** 这是「push 后必须观察结果」的直接证据，
也是本轮最重要的方法学结论：*本地全绿不等于 CI 能过*。
