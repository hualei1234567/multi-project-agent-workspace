**真实写入验证**（不是只看装饰器）：建 release → 置 `approved` → 调 `publish()` →

`resource_id=真实 release id`。

## 三、S-7 · Event Outbox 生产投递

**问题**：`p4_events.dispatch_pending()` 只有定义和测试调用，生产代码零调用方。
outbox 只写不投，事件永久积压，at-least-once 形同虚设。

**做法**：`agents_dashboard.py` 增加常驻 `_event_dispatcher()` 线程——单飞、5s 间隔、

**测试**：`test_outbox_dispatch_marks_dispatched`（真投递并清空 pending）、
`test_outbox_dispatch_is_idempotent`（重跑不再投）、
`test_server_starts_dispatcher_thread`（防改动时误删调用方）。

## 五、D-1 · Execution ↔ Task 追溯

**问题**：12 条 execution 全部 `source='transcript'` 且 `task_id IS NULL`。
但「本来就不属于 Task」和「该关联却没关联上」是两件完全不同的事，只靠 NULL 分不出来。

**schema v19**：`executions` 增加 `link_quality` / `first_seen_source`。

| link_quality | 含义 | 是否计入追溯率分母 |
|---|---|---|
| `linked` | 有确定性证据关联到 Task | 是（且计入分子） |
| `dispatcher_missing_task` | 调度器写的却没 task_id，**真缺陷** | 是 |
| `legacy_unlinked` | transcript 采集的人工会话，本来就没有 Task | **否** |
| `unknown` | 无法判断 | 是 |

**回填规则（`_migrate_v18_to_v19`）**：只认 `dispatch_items.session_id` **精确匹配**
这一种确定性证据。不按时间、不按文本相似度猜 Task。实测 12 条全部 → `legacy_unlinked`。

**新指标** `service.execution_traceability(project_id)` + `GET /api/projects/{id}/executions/traceability`：

- 分母只含「按业务规则应关联 Task」的执行；
- `traceable == 0` 时 `rate` 返回 **`None`** 而不是 `0.0`——「没有可追溯对象」与
  「一条都没追溯上」不能混为一谈；
- 显式区分 `unlinked_defect`（要修）与 `unlinked_legacy`（历史口径）。

**实测**：material / ddp 各 6 条，全部 `legacy_unlinked`，`rate=null`，`unlinked_defect=0`。

## 六、D-2 · 成本口径分离

**问题**：6,780 条 `token_usage_events` 的 `cost_usd` / `price_version` 全为空。
报表把「不知道花了多少」显示成 0 或干脆不显示，两者都是错的。

### 价格版本表（schema v19）

`model_price_versions`：`model_pattern` + `effective_from`/`effective_to` + 四维单价 +
`source`/`source_detail`。**不写死当前单价**。

价格来源是**可复现的推导**，不是抄价目表：`ccusage`（v20.0.46）对同一份 transcript 的
计费是四维 token 的线性函数，用多会话做最小二乘可精确反解单价：

| 模型 | input | output | cache_read | 证据 | 残差 |
|---|---|---|---|---|---|
| `deepseek-v4-1-flash-261017` | $0.15 | $0.60 | $0.003 | 13 会话 | **0.0000%** |
| `deepseek-v4.1-flash-1017` | $0.30 | $1.20 | $0.007 | 9 会话 | **0.0000%** |

生效起点取「该模型首条有证据的会话时间」，早于此时的记录**保持 UNKNOWN**，
不用更晚的价格假装当时就这个价。

**独立交叉核对**：在平台 token 与 ccusage token 完全一致的子集上，
估算 $0.099795 vs ccusage $0.099795，**差 +0.00000000**。公式无损。

### 三档口径

| 档位 | 写入条件 | 报表表现 |
|---|---|---|
| `actual` | provider 账单（CLI `total_cost_usd`） | 真实金额 |
| `estimated` | 命中带生效区间的价格版本 | 估算金额 + price_version |
| `not_billable` | token 为 0，确定不产生费用 | 0，且不进覆盖率分母 |
| `unknown` | 以上都不满足 | **None**，显式披露条数 |

### 回填结果（dry-run → 备份 → 执行）

```
备份：data/platform.db.bak-r2-d2-20261114T163449Z
dry-run：scanned=6780  priced=5449  zero_token=1148  unmatched=183
apply  ：estimated_cost_usd 非空 0 → 6597
```

覆盖率：
- 全库 **96.75%**（5449/5632 应计费事件）
- material 87.58%（$1.728），ddp **100.00%**（$9.498）
- 183 条无价格证据（`deepseek-flash` 早期记录等）**保持 UNKNOWN**，未倒填

### 执行粒度真实成本

执行器现在解析 stream-json 的 `result.total_cost_usd` 并写入
`executions.actual_cost_usd`（`cost_quality='actual'`）。
取不到、负数、非数字一律丢弃 → `unknown`，绝不编数字。

### 报表与 UI

- `service.project_usage()` 同时给出 `cost_24h`（ccusage 会话分摊，近似）与
  `cost_ledger`（逐条事件真实/估算 + 覆盖率），并附 `cost_note` 说明两者不可相减；
- `usage_breakdown()` 返回 `cost_ledger`；
- P4 outcome 成本面板改为「真实账单 / 估算成本 / 成本覆盖率（未知 N 条）/ 零计费事件」；
- 变量名 `cost` 与模块名冲突处已改为 `ledger_cost`，避免后续踩坑。

## 九、遗留与风险（未在 R2 范围内）

   这导致会话级总额对不上（估算合计 $11.23 vs ccusage $19.13）。
   **这是口径差异，不是单价错误**（已在同 token 子集上验证到 8 位小数相等）。
   是否统一口径属于 P2/P3 议题，R2 不做。
2. **`executions` 12 条历史记录全部无 Task 归属**：按规则不伪造。
   真实追溯率要等 R3 出现调度驱动执行后才有非零分母。

   本轮已修一处竞态（会话空态），夹具清理仍依赖测试正常退出。
