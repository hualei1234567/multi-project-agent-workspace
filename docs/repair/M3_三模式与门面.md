## 交付内容

### 1. 三模式（schema v24）

新表 `dispatch_plan_candidates` + `dispatch_plans.mode` 列。

| 模式 | items | candidates | 能派发 | 默认 |
|---|---|---|---|---|
| `shadow` | **0** | ✅ | ❌ | 否 |
| `recommend` | **0** | ✅ | ❌ | **是** |
| `assisted` | ✅ queued | — | 需审批 | 否 |

**核心保证是结构性的**：`shadow`/`recommend` **根本不写 `dispatch_items`**，
而执行器只认 `dispatch_items`——所以这两种模式在结构上不可能起进程。
不是靠"记得别调执行器"。

实测：
```
shadow     items=0 candidates=1 creates_items=False
recommend  items=0 candidates=1 creates_items=False
assisted   items=1 candidates=0 creates_items=True
```

### 2. 候选评分（可解释）

四维加权：优先级 40 / 依赖就绪 20 / 角色能力 25 / 等待时长 15。

实测输出：
```
#1 score=57.79 — 优先级 P1（30 分） · 依赖已就绪（20 分） ·
   角色未登记能力（不加分也不减分） · 等待时长（7.8 分）
```

**没登记能力不减分**，只标记 `capability_unknown`——
用数据缺失惩罚功能是错的。有证据的能力才加分。

### 3. Scheduler Facade（ADR-P3-002）

`app/agent_platform/facade.py`。堵住 `team.py` 绕过 Policy 的路径：

```python
def guard(conn, *, entry, project_id, principal):
    # 1. Kill Switch 优先（秒级停止必须比任何判定都早）
    # 2. Policy 判定
    # 3. 拒绝时 audit_denial 留痕
```

`_team_launch` 现在必须过门面。**principal 从认证上下文传入**，
不从请求体取——否则任何人都能自称 owner 绕过 Policy。

### 4. UI

- 调度页加模式下拉（RECOMMEND / SHADOW / ASSISTED）
- 计划详情按模式分流：assisted 显示可执行项表格，其余显示候选卡片
- 顶部提示条说清楚「这次会不会派发」

## 变更的性质（重要）

**历史计划默认标 `assisted`**，不是 `recommend`。

理由：v24 之前的计划都是"点一下就能执行"的形态，标成 recommend 会撒谎。
新计划由代码显式传 `mode`，默认 `recommend`。

**现有测试的影响**：7 个测试原本调 `create_plan()` 取 `items`，
现在必须显式传 `mode="assisted"`。这不是放宽断言，是语义变清楚了——
"我要一个能执行的计划"现在必须说出来。
