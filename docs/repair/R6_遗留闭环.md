## 二、真实 Canary 可验证

**问题**：平台没有流量路由能力，Release 只能标 SIMULATED，「真实 Canary」无从验证。

**处理**：新增 `release.probe_traffic_entry()`——**声明 LIVE 必须实际探通流量入口**。

```
LIVE 发布 → 实际探测入口 → 连不上就拒绝（traffic_entry_unreachable）
                          → 连得上才允许标 LIVE
```

支持的入口形式：
- `http(s)://host:port/path` —— HTTP 探测
- `tcp://host:port` / `host:port` —— TCP 连接检查

探测用**无代理 opener**：CI 上有 `http_proxy`，用默认 opener 会把本地探测送去代理并误判不可达。

**实测（真实闭环）**：

```
发布: published | mode: LIVE
  流量探测: {'reachable': True, 'detail': 'HTTP 200'}
  有真实流量: True

Canary: canary_598ef1... | 10% 分流
  观测（正常）: canary | breaches: []
  观测（越阈）: stopped | breaches: ['error_rate=0.2 > 0.05', 'latency_ms=800 > 500']
```

**边界说明**：这验证的是「分流入口真实可达 + 停止阈值生效」，
不是「真实用户流量打到新版本」。要后者需要真正的网关/负载均衡，超出平台范围。
但相比之前「只要给个字符串就能标 LIVE」，这已经是实质性收紧。

## 三、调度日志按 attempt 隔离

**问题**：同一调度项重跑时，`seq` 从头开始但 `item_id` 相同，两段日志混在一起，
排查时分不清哪段是第几次执行留下的。这是 R3 实测时亲自撞到的。

**修复（schema v21）**：
- `dispatch_logs` 加 `attempt INTEGER NOT NULL DEFAULT 0`
- 索引改为 `(item_id, attempt, seq)`
- `_append_log()` 增加 attempt 参数，`_spawn()` 从 `dispatch_items.attempt + 1` 取值

**验证**：新增回归测试 `test_dispatch_logs_are_isolated_by_attempt`，
跑两次执行后断言日志中存在 ≥2 个不同 attempt。
