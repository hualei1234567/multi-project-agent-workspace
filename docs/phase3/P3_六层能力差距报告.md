# 六层能力差距报告

> 日期：2026-11-15
> 对照用户给定的六层目标框架，逐层量化差距
> 证据来源：`docs/phase3/audit/` 五份只读审计

---

## 总览

| 能力层 | 完成度 | 判定 | 主要缺口 |
|---|---|---|---|
| 项目管理层 | **90%** | 强 | 项目模板 |
| Agent 资源层 | **30%** | **弱** | Registry 全缺 |
| 任务调度层 | **45%** | 中 | Global Task、三模式、任务拆解 |
| 执行控制层 | **55%** | 中 | Mac Gateway、审批失效 |

| 治理运营层 | **70%** | 中偏强 | 审批闸门空、预算 |

**整体：约 60%。地基扎实，缺的是「资源层」和「跨项目能力」。**

## 层 2 · Agent 资源层 — 30% ★ 最大缺口

| 目标能力 | 现状 | 差距 |
|---|---|---|
| Agent | ⚠️ 只有 `project_agents`（项目内实例） | **缺角色定义注册表**（Role Definition vs Instance） |
| **Skills** | ❌ 仅 `ALLOWED_TOOLS` 里出现 "Skill" 字符串 | **完全缺失**：无定义、无版本、无来源、无权限、无扫描、无审批 |
| 模型 | ⚠️ 只有 `model_price_versions`（价格表） | **缺 Provider/协议能力/上下文限制/工具能力** |
| **Runtime 资源池** | ⚠️ `runtime_services` 能采集健康 | **缺心跳超时、租约、可分配状态、并发上限** |
| **兼容矩阵** | ❌ 无 | 无 Agent×Skill×Model×Runtime 兼容判定 |

**这是结构性缺口。** 现在的「资源」全是隐式约定，系统无法回答：
- 系统里有哪些 Agent 角色？
- 某个角色能用哪些 Skill？哪个版本？
- 某个模型支持多长上下文、哪些工具？
- 某台 Runtime 现在可分配吗？谁占着？

**没有 Registry，调度就只能是「按优先级排序」，做不到 V4.0 要求的「智能匹配」。**

## 关键结论

### 1. 差距集中在一个地方：资源层

六层里五层都在 55% 以上，唯独 **Agent 资源层 30%**。
而且它是**其他层的依赖**：
- 调度要做「智能匹配」→ 需要 Registry
- Gateway 要做「能力上报」→ 需要 Registry
- 治理要做「兼容判定」→ 需要 Registry

**Registry 是唯一的关键路径节点。**

### 2. 唯一的真实安全风险：审批闸门

不是没写代码，是 `policy_rules` 表里 **0 行**。
`policy.decide()` 走到 RBAC 那步，`local-owner` 是 platform_owner → 直接 `return True`。
`requires_approval` 永远是 `False`。

**修复成本极低（几条规则 + 一个申请 API），收益是 P3-M8 的 2 项 P0 转绿。**

### 3. 已经做好的部分不该动

AgentOps 五域、成本三档、事件 Outbox、Kill Switch、项目隔离——
这些都是真实的、有证据的、经得起审计的。**不推倒重建**。

---

## 建议的实施顺序

| 序 | 动作 | 理由 |
|---|---|---|
| **1** | 审批闸门修复 | 安全止损，成本极低，P0 |
| **2** | P3-M0 五份文档 → 用户批准 | V4.0 门禁，不可跳 |
| **3** | **P3-M2 Registry** | 关键路径，解锁调度智能与 Gateway |
| **4** | P3-M3 三模式 + Facade | 依赖 Registry |
| **5** | P3-M5 Global Task + 委派 | 跨项目能力 |
| **6** | P3-M4 Gateway | 依赖 Registry |
| **7** | P3-M6 PWA | 移动端 |
| **8** | P3-M7 预算/效能 + P3-M8 验收 | 收尾 |

**这与 V4.0 蓝图 §4 的 Wave 顺序基本一致，只是把 Registry 从 Wave A 提到更前面，
因为它被其他层依赖得更深。**
